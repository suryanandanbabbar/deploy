2. Business problem and purpose

Enterprises frequently accumulate large portfolios of Alteryx workflows over time. Different teams create workflows that perform overlapping transformations, implement similar business logic, consume the same sources, or produce comparable outputs.

This creates several problems:

* Duplicate ETL processing and redundant workflows.
* Excessive maintenance and operational overhead.
* Poor visibility into upstream and downstream dependencies.
* Limited understanding of transformation logic and data lineage.
* Difficulty determining which workflows can be consolidated, retired, shared, or require further investigation.
* Risk of retiring workflows that support critical business processes.
* Difficulty communicating technical findings to business stakeholders and executives.

The tool is intended to turn Alteryx workflow definitions into structured, evidence-based intelligence that helps teams assess their ETL portfolios and identify rationalisation opportunities.

The goal is not simply to parse XML or ask an LLM to recommend workflow deletions. It is to establish a deterministic technical foundation, enrich it with bounded AI interpretation, and present actionable portfolio-level recommendations with supporting evidence.

The tool supports ETL rationalisation and migration analysis. It should not be represented as automatically executing workflow migrations or deleting production workflows unless the implementation explicitly demonstrates those capabilities.

3. Core functionality

The following describes the intended system capabilities. Verify each capability against the current implementation before claiming that it is complete or production-ready.

3.1 Alteryx workflow ingestion and parsing

Alteryx workflows are commonly represented by .yxmd files. The backend analyses their definitions to extract structural and semantic information, including:

* Workflow tools and their relationships.
* Input and output sources.
* Transformation and processing operations.
* Field-level and schema-related information where available.
* Dependencies between tools and data sources.
* Workflow connectivity and directed graph structure.
* Evidence relevant to understanding business purpose and downstream impact.

The workflow definition is converted into a canonical intermediate representation (IR). This representation is the foundation for subsequent analysis.

Important architectural principle: downstream services should consume the canonical analysis rather than independently reparsing the original .yxmd files or recreating their own interpretations of the same workflow.

3.2 Directed acyclic graph and dependency analysis

The system uses graph-oriented representations to understand workflow execution structure and dependencies.

The analysis supports:

* Tool-to-tool connectivity.
* Source-to-transformation-to-target relationships.
* Upstream and downstream dependency tracing.
* Workflow complexity and structural metrics.
* Evidence for determining whether workflows overlap or share logic.
* Lineage and transformation analysis.

Validate the treatment of cycles, disconnected components, ambiguous connections, missing metadata, and malformed workflows in the actual implementation.

3.3 Data lineage and source-to-target mapping

The application provides lineage-oriented information, including source and target relationships, transformations, and schema or field mappings when the workflow provides sufficient evidence.

Source-to-target mapping (STTM) and lineage should be evidence-driven. The system must distinguish information explicitly present in the workflow from information inferred by an LLM.

Never fabricate field mappings, table names, transformations, or dependencies to fill gaps.

A lineage representation should remain consistent across the workflow overview, detailed analysis, and portfolio-level views.

Special case: some demonstration workflows contain data embedded in Alteryx TextInput tools instead of using file-based input tools. For these workflows, canonical lineage must use labels such as Source Input #1 where appropriate. Internal identifiers such as TextInput #1 (Field1) or Source #43 must not leak into user-facing source names when the canonical Workflow Overview uses the former representation.

3.4 ETL rationalisation recommendations

The tool analyses workflow evidence to identify potential rationalisation opportunities.

The established recommendation categories include:

* CONSOLIDATE: workflows that may be consolidated based on evidence of overlap or compatible functionality.
* RETIRE_CANDIDATE: workflows that may be candidates for retirement, subject to appropriate safety checks.
* SHARED_LOGIC: workflows or components that implement reusable logic.
* REVIEW: cases requiring further investigation.
* NO_ACTION: an internal classification where no rationalisation action is justified.

Confirm the current API and UI representation of these categories before changing their names or meanings.

Retirement recommendations require particularly strict safeguards. Similarity alone is insufficient evidence that a workflow is safe to retire. Downstream dependencies, business criticality, output semantics, source and target relationships, and missing evidence must be considered.

Complexity and criticality should inform risk and prioritisation, not independently establish that two workflows are duplicates or that one can be retired.

The application should provide explainable recommendations, not unsupported conclusions.

3.5 Deterministic fingerprints and candidate detection

The project includes deterministic fingerprinting and candidate-detection logic to identify potentially related workflows.

This is intended to provide a reproducible technical basis for comparisons before any LLM interpretation.

Verify:

* Which workflow attributes contribute to fingerprints.
* Whether normalisation makes equivalent workflows comparable.
* How irrelevant structural differences affect similarity.
* Whether identifiers and ordering produce unstable results.
* How false positives and false negatives are handled.
* Whether results remain deterministic across repeated runs.

Do not replace existing candidate-detection logic with a purely LLM-based comparison.

3.6 LLM-based interpretation and classification

LLMs enrich the deterministic analysis by helping interpret workflow semantics, business purpose, and potential rationalisation opportunities.

The architecture should separate factual extraction from semantic interpretation:

1. Parse the workflow and establish canonical technical evidence.
2. Derive deterministic structural metrics and candidate relationships.
3. Supply relevant evidence to the LLM for bounded interpretation.
4. Validate the LLM output against a strict schema and the available evidence.
5. Reject unsupported or inconsistent claims.
6. Apply deterministic fallback behaviour when the LLM fails, returns malformed output, or produces invalid classifications.
7. Present the result with traceable evidence.

LLMs must not become the source of truth for technical facts that can be extracted deterministically.

The application must not expose credentials, API keys, tokens, or confidential configuration to users through model responses, logs, API responses, or error messages.

3.7 Business-area classification and portfolio intelligence

The tool supports portfolio-level reasoning and grouping workflows by business area or purpose.

An important architectural decision established during earlier development is that business purpose and business-area classification should be generated or established once during upload/canonical analysis, validated, and persisted as canonical data.

Downstream components such as Portfolio, Workflow Overview, and Criticality should reuse that canonical classification instead of independently regenerating it.

The intended safeguards include:

* One authoritative source for business-area classification.
* Stable identifiers for business areas and workflows.
* Support for configured business-area vocabularies rather than a fixed hard-coded list.
* Deterministic fallback behaviour when the LLM classification is unavailable or invalid.
* Idempotent processing.
* Correct aggregation of all configured business-area cards, including areas with zero workflows.
* Consistent workflow counts across views.
* Bounded impact of criticality calculations on recommendations.
* Backward compatibility for legacy records where required.

Critical edge case: a configured business area must still appear when its workflow count is zero. Missing or empty categories must not silently disappear from the interface.

6. Proprietary source-code protection

A major objective is to distribute a functioning application without exposing the proprietary Python implementation to the client in ordinary readable source form.

This is a commercial IP-protection requirement. It is not sufficient merely to package the source directory in a ZIP file or Docker image.

The project explored and implemented a Nuitka-based native compilation strategy.

6.1 Nuitka compilation

The application was investigated for compilation into native Linux binaries and extension modules.

Historical build details include:

* A Linux environment running Python 3.12.
* Nuitka 4.2.2.
* GCC 13 and patchelf.
* A successful standalone backend executable build under deployment/main.dist/awa_server.
* An ELF x86-64 artifact of approximately 151 MB.

This demonstrates that a standalone native build was achieved in that environment. It does not, by itself, prove that the complete application was successfully deployed and tested end to end.

Subsequent planning focused on a Python 3.11, module-by-module compilation approach that preserved the backend/awa and backend/app hierarchy using compiled .so modules and generated package markers.

The exact final Python ABI, Nuitka configuration, and build artifact must be verified before reuse. A .so built for one Python version, ABI, operating system, or CPU architecture is not automatically compatible with another.

6.2 Intended protected artifact

The desired release artifact should:

* Preserve the required runtime package hierarchy.
* Compile proprietary Python modules.
* Retain necessary package initialisation and import behaviour.
* Include required non-code runtime assets.
* Include the correct Databricks Apps startup configuration.
* Exclude tests and development-only resources.
* Exclude .env files and secrets.
* Exclude proprietary plaintext .py files from the production artifact.
* Avoid unnecessary .pyc files and cached source-derived material.
* Remain compatible with the target Databricks Apps runtime.
* Keep individual files within the applicable Databricks Apps constraints, including the previously identified 10 MB per-file requirement where it applies.

Known runtime resources considered during the build include grammar.lark and llm_cache.json. Their necessity and treatment must be confirmed from actual imports and runtime access patterns.

Do not remove a resource simply because it is not Python code. Conversely, do not bundle development files or sensitive caches without justification.

6.3 Module-versus-package issues

During compilation, an error was encountered concerning awa being a module rather than a package and the inability to include package data in that configuration.

This indicates that the compiled package structure, data-file handling, and import semantics require careful validation.

Do not change the source code’s directory structure merely to accommodate an assumed Nuitka packaging model. Preserve the existing layout and select a compilation and packaging approach compatible with it.

6.4 What source protection does and does not mean

Native compilation raises the cost of casual source inspection, but it is not equivalent to cryptographic secrecy or complete tamper resistance.

A technically sophisticated recipient may still inspect binaries, extract resources, analyse runtime behaviour, or attempt reverse engineering.

Docker and ACR protect distribution workflows and artifact identity; they do not inherently conceal source code inside an image.

The release process must therefore validate the contents of the actual artifact rather than assuming that compilation has removed every readable proprietary file.

7. Licensing and kill-switch implementation

A significant milestone was implementing and deploying a licensing mechanism intended to enforce agreed limits on the use of the proprietary application.

The requirement is to allow authorised use while making continued operation dependent on a valid licence and its configured restrictions.

The licensing work has included an Ed25519-based signing and verification chain, Azure Key Vault integration, Databricks secret-scope retrieval, and production-oriented tests.

7.1 Cryptographic architecture

The validated design uses:

1. An Ed25519 private key held through Azure Key Vault.
2. A signing operation used to produce a signed licence artifact.
3. Storage and retrieval of that signed artifact through Databricks secret management.
4. An embedded public key used by the application to verify the signature.
5. Validation of the signed payload’s integrity before relying on its licensing claims.

The intended security property is that the application can verify a licence without possessing the signing private key.

Do not embed the private signing key in the application, compiled binary, container, or client-accessible configuration.

7.2 Validated production identity and configuration

* Product: alteryx-etl
* Environment: production
* Databricks secret scope: alteryx-licenseArtifacts
* Secret name: alteryx-license

The signed artifact was stored and enabled through the configured licensing chain. Retrieval succeeded, returning a payload of 319 bytes.

The signing and verification chain was reported as passing production-identity validation, signature verification, and payload-integrity checks.

These are established historical results. Verify that the deployed environment still uses these identifiers and that the current code and test suite reflect the same configuration.

A stale reference to the earlier hyphenated scope name was found in bundled __pycache__ bytecode after the configuration was changed to camelCase. That was a cleanup concern and must not be mistaken for an active configuration reference without inspection.

7.3 Licensing criteria: expiry, volume and token

The documentation and implementation were subsequently updated to accommodate the additional criteria of volume and token, alongside the existing licensing restrictions.

The intended policy must account for the applicable configured limits and reject further use when the relevant licence condition is no longer satisfied.

However, do not invent the precise semantics of these criteria. Inspect the final LicenseManager, licence payload schema, enforcement call sites, tests, and configuration to establish:

* What volume measures.
* Whether volume is cumulative, per request, per workflow, or otherwise scoped.
* What token measures and whether it refers to LLM token consumption, another usage unit, or a specific application-level quantity.
* How usage is recorded and persisted.
* How limits are calculated and enforced.
* What happens at, below, and above each limit.
* Whether concurrent requests can bypass or incorrectly consume limits.
* How expiry interacts with volume and token restrictions.
* Whether counters survive restarts and deployment replacements.
* What happens when the licensing service, secret scope, or signing infrastructure is unavailable.

The exact production semantics must come from the code and tests, not this handover.

7.4 Kill-switch behaviour

The kill switch is intended to prevent continued use after the agreed licensing period or usage allowance has ended.

The enforcement mechanism must be integrated into the actual execution path. Merely checking a licence in a frontend component or at application startup is insufficient if requests can bypass that check.

Validate the enforcement boundary across relevant API routes and background or scheduled execution paths.

Check for:

* Expired licences.
* Invalid signatures.
* Modified payloads.
* Missing or malformed licensing data.
* Exhausted volume limits.
* Exhausted token limits.
* Concurrent requests and race conditions.
* Process restarts and deployment replacements.
* Clear, controlled failure behaviour.

Do not assume that every scenario above has already been tested successfully.

The kill switch is a commercial licensing control, not a substitute for authentication, authorisation, secure data access, or standard incident-response mechanisms.

12. Key architectural principles that must not be lost

These are important decisions and requirements established during prior work.

Principle A: Canonical analysis is the source of truth

Extract workflow facts once and persist the canonical representation. Do not introduce competing parsers or parallel analysis paths that disagree.

Principle B: Deterministic evidence precedes LLM interpretation

Use actual workflow structure, graph relationships, source and target evidence, and deterministic metrics as the foundation. Use LLMs for bounded semantic interpretation.

Principle C: LLM output requires validation and fallback

Validate schemas, reject unsupported assertions, use stable identifiers, and preserve deterministic behaviour when AI services fail.

Principle D: Rationalisation is risk-sensitive

A recommendation to consolidate or retire a workflow must be supported by technical and business evidence. Complexity and criticality are risk indicators, not standalone proof of duplication.

Principle E: Portfolio aggregation must be complete

All configured business-area cards must render, including those with zero workflows. Workflow counts and classifications must remain consistent across views.

Principle F: Preserve the existing codebase structure

Do not restructure backend/awa, backend/app, or other source directories without a demonstrated technical requirement and explicit consideration of compatibility.

Principle G: Production artifacts must be verified

Do not infer source protection from a successful build. Inspect the final package for plaintext proprietary code, secrets, development artifacts, and required runtime resources.

Principle H: Licensing must be enforced server-side

The licensing mechanism must protect the actual execution boundary and remain separate from ordinary authentication and authorisation.

Principle I: No fabricated results

Never use hard-coded sample recommendations, invented workflow evidence, or fabricated business metrics in production analysis.

Principle J: Backward compatibility matters

Avoid breaking existing workflows, stored analyses, APIs, and UI assumptions while introducing new functionality.
